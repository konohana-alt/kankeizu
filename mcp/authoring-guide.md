# 「かんけいず！（仮）」DSL 作成ガイド（AI向け）

このガイドは、ストーリー原案から演出エンジン用のJSONを生成するAI（Gemini/Claude等）に
読み込ませることを想定しています。生成後は必ず `validate_dsl` ツールでチェックし、
返ってきた errors を0件にすること。warnings は0件が理想だが、意図的なものなら残してよい。

## 0. 全体構造

```json
{
  "nodes": [ ... ],
  "edges": [ ... ],
  "groups": [ ... ],
  "ungroupedArea": { ... },
  "timeline": [ ... ],
  "sources": [ ... ],
  "assets": { ... },
  "mapBackground": { ... }
}
```

`nodes` と `timeline` は必須（1件以上）。それ以外は省略可。

**重要な設計原則：エンジン（`kankeizu_prototype.html`）は完全に汎用であり、特定の物語専用の
コード（特定の人物の肖像画、特定の場所の地図イラスト等）を一切持たない。** そうした素材は
すべてDSL側（`assets`・`mapBackground`）に持たせる。つまり、新しい物語を作るたびに必要なのは
DSL（JSON）1つだけで、エンジン側のコードを変更する必要は無い。

### assets（このDSL専用の画像素材：肖像画・カスタム状態アイコン等）

```json
"assets": {
  "delaunay": { "mime": "image/jpeg", "base64": "..." },
  "sad": { "url": "https://example.com/sad-icon.png" }
}
```

`node.icon`、または5.65章の`statusHistory.statuses[].status`にここで定義したキー（例：
`"delaunay"`、`"sad"`）を指定すると、その画像が使われる。`node.icon`から参照した場合は
フレーム無しの写真として表示される（詳細は2章の`icon`を参照）。

各素材は次のどちらかで指定する：
- `base64`：画像そのもの（PNG/JPEG等）をBase64エンコードした文字列。**どこで開いても確実に
  動く**（推奨）。
- `url`：外部にホストされた画像への直リンク。ファイルサイズを増やさずに済むが、**このDSLを
  claude.aiのArtifactとして公開する場合は読み込めない**（Artifactの実行環境が外部画像の
  読み込みをブロックするため）。自分でHTMLをホスティングする、またはローカルで開く用途に
  限られる。どちらか迷う場合は`base64`を使うこと。

エンジンにあらかじめ用意されている汎用アイコン（`get_known_values`で確認できる`farmer`/
`cook`/`person`等）と衝突しないキー名にすること。

### mapBackground（背景地図の画像素材）

```json
"mapBackground": { "mime": "image/jpeg", "base64": "...", "width": 1123, "height": 947, "opacity": 0.85 }
```

`assets`と同じく、`base64`の代わりに`url`（外部リンク）でも指定できる（Artifact公開時は
読み込めない点も同様）。

- `width`/`height`：画像のピクセルサイズ。**DSLの座標系（`node.x/y`や`group.x/y`）と同じ単位で
  そのまま配置される**ので、実在の地図画像を使う場合は、地図上の実際の場所のピクセル座標を
  そのままノード・グループの`x/y`として使うと、位置がぴったり一致する。
- `opacity`：省略可。省略時は0.85。
- `mapBackground`を省略した場合、背景には何も描かれない（無地）。

## 1. step（ステップID）の考え方 ― 最重要

`timeline[].step` / `edges[].history[].step` / `node.appearsAt` / `node.groupHistory[].step` は
すべて同じ1本の時系列軸を共有する。値は次の2通りのどちらかを選べる：

- **数値の連番**（例: `1, 2, 3...`）。時刻を気にしない、単純な「起きた順番」だけで良い物語向け。
- **タイムスタンプ文字列** `"YYYY-MM-DD HH:MM"`（例: `"2026-06-10 19:00"`）。実際の時刻が意味を持つ物語向け。
  こちらを使うと `schedule`（後述）による生活パターンが有効になる。

**1つの物語の中では、数値とタイムスタンプを混在させない。** 大小比較が意味を失う。

## 2. nodes（登場人物）

```json
{ "id": "yaoya", "label": "八百屋の親父", "x": 160, "y": 260, "appearsAt": 2, "icon": "farmer" }
```

| フィールド | 必須 | 説明 |
|---|---|---|
| id | ✅ | 一意のID |
| label | ✅ | 表示名 |
| x, y | ✅ | 座標（後述のグループ機能を使うなら「無所属時のフォールバック座標」程度の意味しか持たない） |
| appearsAt | — | このstepまで画面に出さない（初登場のポップイン演出付き） |
| icon | — | `"farmer"` `"cook"` `"person"` `"gunfire"` `"clash"` `"punch"` `"argument"` `"cannon"` `"gunpowder_keg"` のいずれか（`get_known_values`で最新一覧を確認）、**または`assets`で定義したキー**（実在の肖像画等）。他の値は頭文字プレースホルダーにフォールバックする。`assets`のキーを指定した場合は、手描き枠の無いフレームレス表示になる（詳細は0章の`assets`を参照） |
| iconHistory | — | `groupHistory`と同じ考え方で、**肖像画を時間経過で切り替える**。`[{ "step": ..., "icon": "..." }]`の配列。最後に到達したエントリの`icon`がそのまま続く。まだ最初のエントリに到達していない間は、上の`icon`（静的な値）が使われる。負傷・老化・変装等、見た目が変わる場面で使う |
| groupHistory | — | 下記4節 |
| schedule | — | 下記4節 |

```json
{ "id": "delaunay", "label": "ド・ローネ侯爵", "x": 0, "y": 0, "icon": "delaunay_calm",
  "iconHistory": [
    { "step": "1789-07-14 15:00", "icon": "delaunay_worried" },
    { "step": "1789-07-14 19:30", "icon": "delaunay_dead" }
  ] }
```

## 3. edges（関係線）

```json
{
  "id": "e1", "from": "yaoya", "to": "cafe", "routing": "arc-bottom",
  "history": [
    { "step": 1, "label": "幼馴染", "style": "solid" },
    { "step": 3, "label": "好き", "icon": "heart", "style": "thick_red", "overlay": true }
  ]
}
```

- `history`は時系列の変化を積み重ねる。**過去のエントリは自動的に画面から消えない**（打ち消し線＋テープで上書き表現される）。削除・上書きの記述は不要。
- **`color`**（推奨）と **`weight`** で線の色・太さを個別に指定できる。旧来の`style`は後方互換のために残してある。
  - `color`：`"default"`（省略時・インク色）/ `"red"` / `"blue"` / `"green"` / `"gold"` / `"purple"` / `"pink"` / `"gray"`。ライトモード・ダークモードそれぞれに最適化されたCSSカスタムプロパティへ自動でマップされる。省略時のデフォルトは `worldConfig.defaultEdgeColor`（それも無ければ `"default"`）。
  - `weight`：`"normal"`（省略時・細め 2.2px）/ `"thick"`（太め 4.5px）。省略時のデフォルトは `worldConfig.defaultEdgeWeight`（それも無ければ `"normal"`）。
  - `style`（後方互換）：`"solid"`（= `color:"default", weight:"normal"`）/ `"thick_red"`（= `color:"red", weight:"thick"`、overlay演出も自動発動）。新規DSLでは`color`＋`weight`を使うこと。
- `overlay: true`を指定すると、上書き演出（打ち消し線＋マスキングテープ）が発生する。旧来の`style: "thick_red"`も引き続きoverlayを自動発動するが、**新記法では`color`と`overlay`は独立しているため、赤でない色でもoverlayを付けられるし、太くてもoverlayを省略できる**。
- レイヤー順（どの線が手前に来るか）はエンジンが自動計算する。記述順は気にしなくてよい。
- 長さが画面に対して長すぎる関係線は、エンジン側が自動的に簡易表示（短い矢印スタブ）に切り替える。DSL側で何かする必要はない。
- **`history`の各エントリに`soundEffect`を書いても効果は無い**（後述の`timeline[].soundEffect`と混同しないこと。フラッシュ演出のトリガーはtimeline側だけが持つ）。
- `routing`：省略可。`"straight"`（省略時のデフォルト、両ノードを直線で結ぶ）または`"arc-bottom"`
  （両ノードの下端同士を、下向きに膨らむ半円で結ぶ）。人物の下（足元）から相手の足元へ弧を
  描く、独特な見た目にしたい場合に使う。
- `history[].icon`：省略可。指定すると、`label`（文字列）の代わりにアイコンを表示する
  （`label`自体は引き続き必須——アイコンが読み込めなかった時のフォールバックとして使われる）。
  組み込みは`"heart"`（♥）。それ以外の文字列を指定した場合は、`node.icon`や
  `statusHistory.status`と全く同じ仕組みで、`assets`（0章参照）の同名キーから画像を探す。
  ```json
  { "step": 5, "label": "相思相愛", "icon": "heart" }
  ```

## 4. グループ（所属）と生活パターン

グループは「アンカー座標＋半径を持つ、キャンバス上のエリア」。ノードはグループの中に自動配置され、
所属が変わると実際にそこへ移動する（アニメーション付き）。

```json
"groups": [
  { "id": "shotenkai", "label": "商店会", "x": 200, "y": 260, "radius": 160 }
],
"ungroupedArea": { "x": 350, "y": 60, "radius": 100 }
```

ノード側は2つの方法で所属を指定できる。**優先順位は `groupHistory` > `schedule` > 固定座標。**

- **`groupHistory`**：ドラマ上の一度きりの変化（脱退・寝返り・移籍など）。
  ```json
  "groupHistory": [ { "step": "2026-06-10 19:00", "groupId": "hantai" } ]
  ```
  `groupId`に`null`を指定すると「無所属」（`ungroupedArea`へ）になる。
  一度設定した所属は、次のgroupHistoryエントリで上書きされるまで**持続する**（時間が経っても自動では戻らない）。

- **`schedule`**：「朝は家、昼は店」のような毎日繰り返す生活パターン。timeline側がタイムスタンプを
  使っている場合のみ機能する（数値stepの物語では使えない）。
  ```json
  "schedule": [
    { "time": "06:00", "groupId": "ie" },
    { "time": "09:00", "groupId": "shotenkai" },
    { "time": "21:00", "groupId": "ie" }
  ]
  ```
  `time`は`"HH:MM"`（日付なし、毎日この時刻になったら適用）。深夜〜早朝などどのエントリの時刻もまだ来ていない場合は、前日最後の状態が続いているとみなされる。

- どちらも指定しなければ、ノードは`x, y`の固定座標のまま動かない。

**同じグループ内の各ノードの位置は、そのノード自身の所属が変わらない限り動かない**（他のメンバーの出入りに影響されない）。これは意図的な設計で、図の安定性を優先している。

### radiusの自動拡大と「縮まない」ルール

`radius`は宣言した値のままではなく、エンジンが**物語全体を通した同時最大人数**から逆算し、
足りなければ読み込み時に自動で底上げする。狭すぎて人が重なって見える、という問題は
基本的にAI側が気にする必要はない（`validate_dsl`の警告も参照）。

ただし、**一度広がった`radius`はセッション中ずっと縮まらない**（増分モードでDSLが
少しずつ育つ際、一時的に人数が少なく見積もられて意図せず縮むのを防ぐため）。もし
物語の中で本当に「エリアが手狭になった／広くなった」という縮小が明記されている場合は、
該当するgroup（または`ungroupedArea`）に`"allowShrink": true`を付ける。これを付けた
回だけ過去の記録を無視して縮小が反映され、その新しい値が次回以降の下限になる。

```json
{ "id": "shotenkai", "label": "商店会", "x": 200, "y": 260, "radius": 100, "allowShrink": true }
```

`allowShrink`を付けない限り、AIは`radius`の値そのものを細かく気にしなくてよい
（小さめの値を書いておいても、必要な分は自動で広がる）。

## 5. timeline（ナレーション＋カメラ）

```json
{
  "step": "2026-06-10 19:00",
  "narrative": "商店街の再開発を巡り、八百屋は商店会を離れ、反対派に加わった！",
  "focus": { "edgeId": "e1", "zoom": 1.25 },
  "activeEdge": "e1",
  "soundEffect": "strikethrough",
  "duration": 4000
}
```

- `narrative`は画面下部にタイプライター表示される。長すぎる（120字超）と折り返しが多くなるので、1〜2文程度に収める。
- `focus`は3パターン：
  - `{ "nodeId": "yaoya" }` … 単独フォーカス
  - `{ "nodeIds": ["yaoya", "cafe"] }` … **複数人を同時に画面に収めたい時は必ずこれを使う**。ナレーションが2人以上について語っているのに`nodeId`（単数）しか指定しないと、片方が画面外になる。
  - `{ "edgeId": "e1" }` … 特定の関係線（その両端の2人）にフォーカス
  - `zoom`はあくまで「希望値」。対象が画面から切れそうな場合は自動的に引きで補正されるので、大きめの値を指定して構わない。
- `focus`を省略すると、その時点で登場済みの全員を見渡す引きの画角になる。
- `activeEdge`：そのstepで「今まさに動きがあった」エッジを明示する。`focus.edgeId`と同じ値でよい。
- `soundEffect`：**timelineエントリにこれを指定した場合のみ**、フラッシュ演出が発生する。値によって演出の種類が変わる（下記「戦闘エフェクト」参照）。認識されない値は、従来通りの汎用フラッシュ（赤い輪）になる。`edges[].history[]`側に書いても効果はない（前節参照）。
- `duration`：自動再生モード時、このステップを何ミリ秒表示してから次に進むか（省略時は3600ms）。手動でタップ送りする場合は無関係。

## 5.5 戦闘・対立エフェクト（soundEffectの認識される値）

`soundEffect`に次の値を指定すると、それぞれ見た目の異なる演出になる。`focus`（`nodeId`/`nodeIds`/`edgeId`のいずれか）の位置に表示される。

| 値 | 演出 | 物理的暴力か |
|---|---|---|
| `"gunfire"` | 銃撃：小さな火花（マズルフラッシュ）が数発パッと散る | ✅ |
| `"cannon"` | 砲撃：大きな爆発＋ゆっくり立ち上る煙 | ✅ |
| `"clash"` | 斬り合い：交差する斬撃線が一瞬閃く（刃物） | ✅ |
| `"punch"` | 殴打：赤いギザギザの衝撃星が時間差で数発入る（素手） | ✅ |
| `"argument"` | 口論：マスタード色のジグザグ「怒鳴り声」マークが上向きに散る | ❌（非物理） |

**`"argument"`と`"punch"`はあえて別の演出にしてある**：暴力（銃撃・砲撃・斬り合い・殴打）は赤〜オレンジ系の色で統一し、非物理の言い争いは意図的に別の色（マスタード）にして、血や衝撃を連想させない見た目にしている。口論が殴り合いに発展する場面では、`"argument"`から`"punch"`へと使う値を切り替えることで、その境界（言葉から物理的暴力への転換点）を演出で示せる。

いずれも`"light_"` `"medium_"` `"heavy_"`の接頭辞を付けて強度を指定できる（例：`"heavy_cannon"`、`"light_argument"`）。**接頭辞を省略すると`"light"`扱いになる**（方針：疑わしきはライトに。強度が不明・未指定の場合は、常に控えめな側にする）。強度が上がるほど、火花・衝撃・怒鳴り声マークの数や大きさ・持続時間が増す（`"heavy_cannon"`は着弾点が複数、`"heavy_punch"`は連打の回数が増える）。

上記5つ以外の値（例：`"strikethrough"`、`"surrender"`のような説明的な文字列）は、従来通りの汎用フラッシュ（赤い輪）にフォールバックする。関係性の変化や決着など、対立の具体的な種類を演出で示す必要がない場面では、こちらを使えばよい。

```json
{ "step": "...", "narrative": "口論はやがて掴み合いに発展した。",
  "focus": { "edgeId": "e1" }, "soundEffect": "argument" }
```
```json
{ "step": "...", "narrative": "ついに殴り合いになった。",
  "focus": { "edgeId": "e1" }, "soundEffect": "heavy_punch" }
```

## 5.6 関係性エフェクトの設計原則（新しい種類が必要な場合）

商店街の口論もあれば、剣と魔法の決闘も、石器時代の小競り合いもある。ストーリーごとに何が
自然かは幅広いので、**時代やジャンルごとの固定プリセットは用意していない**。既存の5種類
（`gunfire`/`cannon`/`clash`/`punch`/`argument`）で足りない場面が出てきたら、以下の原則に
従って**新しい種類をその場で設計してよい**（実際に描画へ反映するにはエンジン側の実装が
必要なので、ストーリー制作の依頼者にその旨を伝え、追加を依頼すること）。

**設計原則**：

1. **物理か非物理かを、まず色で決める。** 暴力（殴る・斬る・撃つ・爆発させる等）は赤〜
   オレンジ系の色で統一する。非物理（言い争い、威嚇、交渉決裂等）は暴力を連想させない
   別系統の色にする（`argument`はマスタード色）。この区別を曖昧にしない。
2. **強度は共通スケールに乗せる。** `light`/`medium`/`heavy`はそれぞれおおよそ0.55倍/1.0倍/1.7倍
   というスケール係数を持ち、粒子の数・大きさ・持続時間に反映する。新しい種類を作る時も
   この3段階を踏襲する。
3. **安定した乱数で配置する。** 火花や衝撃点の位置は、毎フレーム再抽選せず、ステップIDなどを
   シードにした安定した乱数で一度だけ決める（チラつき防止）。
4. **短時間で消えるフラッシュとして実装する。** 目安0.3〜1.5秒。長く残しすぎない。
5. **物理エフェクトは`focus`の位置に表示する。** ノード・エッジの座標系にそのまま乗せられる
   設計にする（独自のレイヤーや座標系を作らない）。
6. **可能ならOpenMojiのアイコンを重ねる。** 手描きの火花・線だけでなく、実際の絵文字アイコン
   （銃🔫・ナイフ🗡️・拳👊・スピーカー📢・爆弾💣）をSVGで埋め込み、手描き演出の中心に重ねて
   描くと、何が起きているか一目で伝わりやすくなる。現在5種類全てにアイコンが入っている。
   新しい種類を追加する時も、その暴力・言動を象徴する絵文字を探して同じように組み込むとよい
   （ノードの`icon`と同じ仕組み・同じライセンス表記を使い回せる）。

**新しい種類の例**（あくまで例。実際に必要になった時点で、上記原則に従ってエンジンに追加する。
象徴的な絵文字があるかも一緒に確認するとよい）：
- 剣と魔法の世界観で、殴打や斬撃とは別に魔法攻撃を表現したい → `"spell"`（発光する粒子が
  弧を描いて収束する等、暴力だが刃物・銃撃とは異なる質感にする。✨や🪄のようなアイコンが使える）
- 石器時代で、素手の殴打とは別に投げ槍・石斧のような原始的武器を表現したい → `"primitive_weapon"`
  （🪓や🔱等）
- 威嚇はするが実際には手を出さない緊張状態を、口論より一段階強く見せたい → `"standoff"`
  （非物理、argumentより激しいがpunchには至らない中間の演出）

新しい種類を思いついたら、それが物理か非物理か（原則1）をまず確定させ、`get_known_values`で
既存の値と衝突しないか確認してから、ストーリー制作の依頼者・実装者に追加を依頼すること。

## 5.65 statusHistory（人物の状態表現：困惑・汗・死去等の漫画的表現）

`node`に`statusHistory`（`groupHistory`と同じ考え方の配列）を追加すると、その人物の肖像画の上に
漫画的な状態アイコンを重ねて表示できる。最後に到達したエントリの`statuses`（配列）がそのまま続く。
**1つのエントリに複数の状態を同時に指定できる**（例：きらめき＋薔薇のフレームを同時に）。

```json
{ "statusHistory": [
  { "step": "...", "statuses": [ { "status": "sweat", "corner": "top-right" } ] },
  { "step": "...", "statuses": [
    { "status": "sparkle", "corner": "top-right" },
    { "status": "roses" }
  ] }
] }
```

- **コーナー配置タイプ**（`corner`を指定する）：`"sweat"`（困惑・冷や汗💦）/ `"angel"`
  （死去・天使の輪と羽👼）/ `"anger"`（怒り💢）/ `"dizzy"`（動揺・目眩💫）/ `"sparkle"`
  （喜び・輝き✨、常にきらめくアニメーション付き）/ `"question"`（疑問❓）。
  `corner`は3×3の9通り：`"top-left"`（省略時のデフォルト）/`"top-center"`/`"top-right"`/
  `"middle-left"`/`"middle-center"`/`"middle-right"`/`"bottom-left"`/`"bottom-center"`/
  `"bottom-right"`。**エンジン側が、そのノードで実際に表示されている画像の範囲（縦横比に応じて
  変わる）を基準に、はみ出さない位置へ自動的に配置する**ので、写真の縦横比を気にして角を選ぶ
  必要はない。**肖像画の顔は中心付近にある前提**で、顔と重ならない位置を選ぶ。実際の肖像画を
  見て、顔がどちら寄りにあるか確認してから選ぶこと（例：横顔で右を向いている肖像画なら、顔の
  ある右側ではなく左側を選ぶ）。
- **フレームタイプ**（`corner`は無視される）：`"roses"`（少女漫画の王子様演出）。**顔（写真）の
  左右の縁**に、その写真と同じ高さの薔薇を1輪ずつ添える。回転はさせず正立のまま静止表示する。
  縦横比を問わず、そのノードの実際の表示範囲（getNodeContentBounds）を基準に位置・大きさが
  決まるので、顔の位置を気にせず使える。
- **カスタム状態（組み込みの語彙に無い、任意の文字列）**：`status`は上記7種に限らない。
  `assets`（0章参照）に同名のキーで画像を用意すれば、`"sad"`のような独自の状態をいくつでも
  追加できる（`node.icon`が`assets`から画像を探すのと全く同じ仕組み）。カスタム状態を使う場合は
  `type`（`"corner"`または`"frame"`、省略時は`"corner"`）も指定すること。

  ```json
  { "statusHistory": [{ "step": "...", "statuses": [
    { "status": "sad", "type": "corner", "corner": "bottom-right" }
  ] }] },
  "assets": { "sad": { "mime": "image/png", "base64": "..." } }
  ```
- **文字列（セリフ）で表現する**：アイコンの代わりに`text`（文字列）を指定すると、吹き出し風の
  バナーにその文言をそのまま乗せて表示できる。`assets`の用意は不要。位置（`corner`）は
  他と同じ9マスから選べる。`status`と`text`はどちらか一方が必須（両方は不可）。

  ```json
  { "statusHistory": [{ "step": "...", "statuses": [
    { "text": "食べ物をくれッ！", "corner": "top-center" }
  ] }] }
  ```
- これらのアニメーション（きらめきの拍動）は、GIF画像等を使わずcanvas上でリアルタイムに
  描いている。時間経過だけで動くので、DSL側で何かする必要はない。
- 関係線（`edges`）が非常に短く、ラベルや矢印が窮屈で読みにくい場面（例：決着・退場の場面で
  当事者同士が隣接している時）では、関係線を無理に読ませようとするより、この`statusHistory`で
  結果（死去・困惑等）を人物側に表現する方が伝わりやすいことがある。

## 5.7 閲覧側の操作（DSLの記述とは無関係、エンジンが標準で提供する）

以下はDSLに何か書く必要はなく、エンジン（`kankeizu_prototype.html`）側が誰でも使える機能として
標準搭載している。DSL制作時に意識する必要はないが、閲覧者ができることとして把握しておくとよい。

- **表示モード切り替え**：画面右上のボタンで「ダイナミックモード」（`focus`に合わせてカメラが
  動く、既定の動作）と「俯瞰モード」（物語全体を1枚に収めた固定カメラ。ステップが進んでも
  動かない）を切り替えられる。俯瞰モードは、大人数が入り乱れる場面や、複数拠点間の移動を
  一度に見渡したい時に向く。
- **拡大縮小・移動（パン）**：スマートフォンでは1本指ドラッグで地図を移動、2本指ピンチで
  指の中心を軸に拡大縮小できる。PCではマウスドラッグで移動、ホイールでカーソル位置を軸に
  拡大縮小できる。これらの手動操作はいつでも自由に行えるが、**ストーリーが次のステップへ
  進むと、通常のフォーカス制御（`focus`に基づく自動カメラ）が改めてそのステップの位置へ
  アニメーションで戻る**（手動操作は「一時的な自由観察」であり、物語の進行を妨げない）。
  タップ／クリック（動かさなかった場合）は今まで通り次のステップへ進む操作として扱われる。

## 6. よくある失敗パターン

1. **2人以上が話しているのに`focus.nodeId`（単数）しか使っていない** → 片方が画面外になる。`nodeIds`を使う。
2. **`appearsAt`を忘れて、後から出てくるはずの人物が最初から画面に出てしまう**。
3. **`groupHistory`の最初のエントリのstepを、そのノードが実際にそのグループにいるべき最初のtimeline stepより後にしてしまう** → その間、固定座標にフォールバックしてしまう。
4. **`schedule`を使っているのに、timelineのstepが数値の連番になっている** → scheduleが機能しない（`schedule`は時刻ベースのため）。
5. **同じ物語の中でstepの数値とタイムスタンプを混在させる** → 順序が壊れる。
6. **一度もfocusで参照されないノードを作ってしまう** → 存在するのに画面に映らないまま話が終わる。
7. **グループの`radius`が、後から増える所属人数に対して狭すぎる**：物語の文章には「エリアが
   手狭になった」とは通常書かれないため、これは読解では気づけない。ただしエンジン側が
   読み込み時に自動でradiusを底上げするので、**AI側で対応は必須ではない**。`validate_dsl`の
   関連warningも、対応必須のエラーではなく参考情報として扱ってよい。
8. **一度広がったエリアが、物語の途中で縮んでほしいのに縮まらない**：エンジンは安全のため
   「一度広がったradiusはセッション中縮まない」がデフォルト。**物語の中で本当に規模縮小が
   明記されている場合**（人が減った、エリアが縮小した等）は、該当する`groups`の要素
   （または`ungroupedArea`）に`"allowShrink": true`を付ける。次節も参照。
9. **`edges[].history[]`に`soundEffect`を書いて、フラッシュ演出が出ると期待してしまう** →
   効果があるのは`timeline[].soundEffect`だけ。エッジのhistory側に書いても無視される。

## 6.5 規模の縮小を明示的に表現したい場合

エリアの拡大縮小には次のルールがある：

- **拡大**：エンジンが自動で行う。DSL側で気にする必要はない。宣言する`radius`は
  「最低限これくらい」という目安の値でよく、実際に必要な分はエンジンが自動的に広げる。
- **縮小はデフォルトでは起きない**：一度広がったradiusは、そのセッション中ずっと
  縮まらない（増分モードでDSLが少しずつ育つ際、一時的に人数が少なく見積もられて
  意図せず縮むのを防ぐための安全策）。
- **縮小を明示的に許可する**：原案の中で「反対派の勢いが弱まり、集まる場所も手狭になった」
  のように、**規模の縮小そのものが物語の表現として明記されている場合のみ**、該当する
  グループ定義に`"allowShrink": true`を付ける。これを付けた回だけ、過去の記録を無視して
  実際の縮小が反映される。以後はその新しい値が次の下限になる（再度`allowShrink`を
  付けない限り、そこからさらに縮むことはない）。

```json
{ "id": "hantai", "label": "反対派", "x": 520, "y": 380, "radius": 90, "allowShrink": true }
```

**判断基準**：規模の縮小が原案テキストに明記されている（あるいは明確に読み取れる）場合のみ
`allowShrink`を付ける。単に「今回の入力にたまたま人数が少なかった」だけでは付けない
（それは意図的な縮小ではなく、単なる一時的な状況なので、広いままで問題ない）。

## 7. worldConfig（ストーリー初期設定）

DSL本体とは別に、ストーリー全体のデフォルト値をまとめたJSONファイル（`world-config.json`）を
用意しておくことで、DSL生成時の判断をAIに毎回説明する手間が省ける。
`check_ambiguous_conflict_terms` に `worldConfig` として渡すと機能する。
テンプレートは `get_world_config_template` で取得できる。

### フィールド一覧

| フィールド | 省略 | 値の選択肢 | 説明 |
|---|---|---|---|
| `worldName` | 可 | 任意の文字列 | ストーリー名（メモ用） |
| `violenceLevel` | — | `none` / `unarmed` / `bladed` / `firearms` / `any` | 曖昧な対立表現の初期設定（上限ではない）。物語中に特定の武器が明文化されれば、こちらより優先される |
| `maxIntensity` | — | `light` / `medium` / `heavy` | 自動解決時の強度の上限 |
| `defaultIntensity` | 可 | `light` / `medium` / `heavy` | 曖昧な対立表現の既定強度。省略時は `light`（疑わしきはライトに） |
| `defaultEdgeColor` | 可 | `default` / `red` / `blue` / `green` / `gold` / `purple` / `pink` / `gray` | 関係線の `color` 未指定時のデフォルト色。省略時は `default`（インク色） |
| `defaultEdgeWeight` | 可 | `normal` / `thick` | 関係線の `weight` 未指定時のデフォルト太さ。省略時は `normal` |
| `allowedKinds` | 可 | 文字列の配列 | 対立種類の選択肢をこの範囲に絞る（例：`["argument","punch","clash"]`）。省略時は全種類を提示 |
| `notes` | 可 | 任意の文字列 | 自由記述のメモ |

### violenceLevel の詳細

| 値 | 意味 |
|---|---|
| `none` / `verbal_only` | 口論のみ。物理的暴力は想定しない |
| `unarmed` | 素手の小競り合いまで |
| `bladed` | 刃物・剣まで |
| `firearms` | 銃器まで |
| `any` | 大砲等、上限なし |

**重要**：`violenceLevel` は「上限（キャップ）」ではなく「何も書かれていない時の初期設定」。
物語の展開で特定の武器が明文化された場合（`resolvedBy: "explicitInStory"`）は、
この設定に関わらずそちらが優先して反映される。

### defaultEdgeColor の使い方

ストーリーの世界観に合った色をデフォルトにすることで、DSL側の各エントリに `color` を
毎回書かなくてもよくなる。特定の関係だけ色を変えたい場合は、そのエントリだけ `color` を指定すれば
worldConfigの設定より優先される（DSLの明示値が常に勝つ）。

```json
{ "worldName": "宮廷陰謀劇", "defaultEdgeColor": "purple", "defaultEdgeWeight": "normal",
  "violenceLevel": "bladed", "maxIntensity": "heavy", "defaultIntensity": "medium" }
```

## 8. 生成後の手順

1. DSL（JSONオブジェクト1つ）を生成する。前置き・説明文・Markdownのコードフェンスは付けない。
2. `validate_dsl` ツールにそのまま渡す。
3. `errors`が1件でもあれば、指摘に従って修正し、再度検証する。0件になるまで繰り返す。
4. `warnings`は、意図的なものでなければ修正を検討する。
